## Separate native diagnostic

`native-memory-validation` branches before model receipts, loader hooks, display,
Vulkan discovery and backend initialization. Its private policy permits one phase:

- `telemetry`: Direct pool/largest available span, CPU heap consumption and
  fallbacks, Flexible availability, and individually named raw kernel counters.
- `virtual-16KiB`: a 16 KiB no-access reservation, protection query and completed
  release, after telemetry and its normal shutdown pass in this boot.
- `direct-io`: bounded aligned reads through at most one 8 MiB CPU window, after
  the tiny virtual phase and its normal shutdown pass in this boot. A distinct
  fixed fixture must pass identity, complete SHA256 and CPU resource retirement.

Each phase requires its own ordinary launch/owner binding, durable result,
normal OS close and fresh CPU admission. Before/after memory observations are
saved. Every opaque native call has a preceding and returned journal stage.
An outside timeout cannot cancel such a call; an unknown result does not permit
speculative release, title replacement or another attempt.

The CPU heap consumes Direct memory and is not an additional physical pool.
Flexible availability and vm0 free/inactive counts retain their separate names.
The latter are not converted into process-available or immediately reclaimable
RAM. These diagnostics do not admit full-model memory or substitute for the
still-strict model OS-memory gate. Old-boot full-model integrity bindings remain
invalid for execution in the new boot.
